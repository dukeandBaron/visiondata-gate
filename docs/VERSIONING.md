# 版本与兼容策略

版本号帮助使用者判断能否升级和复现，不表示功能多少或比赛阶段。

## 四种不同的版本身份

| 对象 | 当前形式 | 如何确认 |
| --- | --- | --- |
| 软件包 | Python、Web、Cargo/Tauri 当前为 `0.1.0` | 对照各包元数据和具体构建回执 |
| 接口与工件 | 如 `visiondata-gate.rulepack.v1`、`visiondata-gate.industrial-skill-receipt.v1` | 固定 Schema/协议和对应验证函数 |
| Skill、算法与规则包 | 内置示例显式锁定各自 `1.0.0` | 检查 manifest、算法版本、参数和内容摘要 |
| 数据、模型和安装产物 | 快照/父子版本、commit、build identity、SHA-256 | 核对内容与来源绑定，不从文件名或日期猜测 |

`DynamicBench-v1/v2/v3/v4` 是不同实验协议，不是软件版本递增。

## 当前是 0.1 工程迭代

当前不是全 API 稳定的 1.0 产品。包根兼容入口以 [PUBLIC_API](PUBLIC_API.md) 为准；目前只有 `GateDecision` 位于包根 `__all__`。其他模块调用应固定 commit、锁文件和相关协议。

历史上存在内容不同、软件元数据同为 0.1.0 的本地候选。使用它们必须同时记录 tag、源码身份和安装器 SHA，不能仅按 `0.1.0` 判断内容相同，也不能推定同版本覆盖升级已验证。

本轮不修改软件版本或历史 Release。后续正式发行维护原则：

- 已发布版本和附件保持不可变；内容变化形成新发布身份和摘要。
- `0.x` 阶段也记录破坏性变更，不以“尚未 1.0”忽略消费者。
- 未来稳定公共 API 的版本递增遵循 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)。
- build metadata 不参与版本优先级；新 build ID 不能代替安装升级验证。

## 修改哪一层，就复验哪一层

| 变更 | 必须检查 |
| --- | --- |
| 字段、枚举、默认值或权限 | Pydantic、JSON Schema、HTTP/TypeScript 消费者、旧输入和失败路径 |
| 摘要、规范化或证据定位 | 固定输入的跨语言摘要、历史读取和旧工件重放；不原地改写旧工件 |
| Skill、阈值或算法 | 精确版本注册、确定性、缺输入、输出越界、回执验证和恢复 |
| 依赖或桌面组件 | 锁文件、许可证/SBOM覆盖、构建、提取资源、原生登录/安装及回退 |
| 文档或示例 | 本地链接、真实命令、示例执行、许可证来源和公开清单 |

可选字段也可能不兼容：严格字段集合或 `additionalProperties=false` 的消费者会拒绝新字段。必须通过消费者测试验证。

## 迁移清单

1. 在 PR 和 [CHANGELOG](../CHANGELOG.md) 说明旧/新合同、影响入口和迁移方式。
2. 保留仍在使用的读取器，或提供显式迁移；不直接删除旧入口。
3. 使用旧版本固定样本和错误输入回归；旧输入不能获得新权限。
4. 验证后再声称兼容；数据库、凭据和外部数据路径不能只靠换回 EXE 回退。
5. 新产物生成新的回执和摘要；发布状态以该产物验证为准。

历史阶段见 [版本演进](VERSION_EVOLUTION.md)，最近候选见 [Releases](https://github.com/dukeandBaron/visiondata-gate/releases)。源码、静态站、安装包、模型效果和生产决定分别验收。
