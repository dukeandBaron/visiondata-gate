# VisionData Gate：Agent 平台架构

VisionData Gate 服务于工业视觉训练与发布前的数据治理。算法工程师提交图像和标注，系统测量数据质量、生成门禁结论，将整改责任交给具名人员，并用新版本复验。

这里的 **Agent OS** 指应用层的运行与治理平台：统一管理任务、工具、模型配置、证据、权限和版本。VisionData Gate 已具备其中的任务与证据基础；当前产品定位仍是**工业视觉数据门禁 Agent 工作台**。它运行在 Windows 和 Python/Web 环境中，没有操作系统内核，也没有完成通用分布式 Agent 调度。

## 状态机、编排与模型分别做什么

| 组成 | 职责 | 对应实现 |
| --- | --- | --- |
| 生命周期与持久化 | 保存任务、事件、审批，区分执行完成与业务裁决 | `product_service.py`、`task_store.py` |
| 编排 | 根据执行路径规划工具；Incident 路径记录假设、证据缺口与 Worker 选择 | `product_runs.py`、`incident_agent_kernel.py`、`worker_selection.py` |
| 确定性工具 | 计算曝光、清晰度、重复、标注与覆盖指标 | `tools.py`、`duplicates.py` 等 |
| 规则裁决 | 对测量事实应用冻结合同，签发门禁结论 | `policy.py` |
| 人工与整改 | 选择方案、批准范围、操作派生版本、启动 Child Run | `capa.py`、`product_service.py` |
| 证据与交付 | 绑定来源、版本、执行结果与摘要，供 API 和工作台核验 | `audit_envelope.py`、`governed_outcome.py` |

状态机控制哪些步骤允许发生；编排决定当前调用哪些工具；模型可以在支持的入口提供规划建议。三者不能互相替代。完整的执行图和审计图也不能直接解释为一个已部署的分布式调度器。

## 三条执行路径

### 图像工作簿：单图取证

上传、选图、运行取证后，工作台核对源字节、基础像素统计、同字节资产、标注和工单记录。这里的 `DUPLICATE_REVIEW` 是有证据引用的处置建议。

同一张图片上传两次，可以证明工作簿中存在相同字节的两条资产记录。没有可靠划分记录时，不能进一步声称已经发生 Train/Val 泄漏。资产级重复问题不需要人为绘制缺陷框。

### 工作簿快照：项目级门禁与 CAPA

```mermaid
flowchart LR
    A[上传图像与保存标注] --> B[冻结项目快照]
    B --> C[创建任务与人工批准计划]
    C --> D[确定性工具测量]
    D --> E[Finding 与门禁工单]
    E --> F[人工选择和批准 CAPA]
    F --> G[私有派生版本]
    G --> H[同合同 Child Run]
    H --> I[复验结果与责任队列]
```

`run_operator_snapshot_product_task` 使用当前快照的白名单工具完成一轮确定性测量，并生成可供 CAPA 消费的交付物。这条路径当前记录 `dynamic_task_count=0`、`replan_count=0`，不自动调用外部模型。

单图取证与项目门禁之间通过服务端重新核验并封存快照交接。单图建议不会被当作项目级最终 Finding 直接写入；项目任务必须重新执行测量。像素工单与受控 CAPA 也是两类记录：前者绑定 BBox 修订，后者绑定 Parent Task、门禁工单、整改计划和审批摘要。

Child Run 的成功含义是：在冻结合同下复验新版本。执行完成、重复消失、全部门禁通过和生产批准是不同结果，需要分别读取。

完全重复的整改范围限定为经批准的 `EXACT_DUPLICATE` 工单：服务端重新测量重复关系，核对划分、类别、工况和标注身份一致，并确认保留一份不会破坏覆盖要求。随后将其余副本排除出派生清单，重新生成快照与摘要。工单是否关闭由 Child Run 实测决定。近重复、跨划分或标注冲突不通过这条规则自动处理。

### Incident：证据驱动的案件编排

Incident 路径额外组织竞争假设、证据缺口、Worker 选择、预算和人工中断后的续跑记录。模型规划建议受到模式、白名单和预算限制。是否发生动态补证，应以该案件实际保存的执行回执为准。

DynamicBench 是项目自建的编排验证。其结果不能用于声称任意上传图片都触发了动态规划，也不能替代工厂验证。

## BYOP / BYOK 与 BYOL

- **BYOP（Bring Your Own Planner）**：为支持模型规划的 Incident 入口接入规划提供方。`off`、`shadow`、`gated`、`replay` 的应用范围见 [Planner 合同实现](../src/visiondata_gate/incident_model_planner.py)。
- **BYOK（Bring Your Own Key）**：由用户配置工作空间内的提供方凭据。保存配置不等于该任务已经调用模型；要检查具体运行绑定与调用回执。
- **BYOL（Bootstrap Your Own Latent）**：通常指视觉自监督学习方法，不是本项目的编排架构。

外部模型接入不意味着把原图发送给模型，也不赋予模型审批 CAPA 或生产放行的权力。具体配置见 [模型配置与平台工作流程](PRIVATE_AGENT_PLATFORM_WORKFLOW.md)。

## 向 Agent 平台演进的顺序

| 优先级 | 工作 | 验收方式 |
| --- | --- | --- |
| 当前 | 任务交接清楚、读取失败可恢复、本地启动与重新打开可靠 | 上传后能进入同项目 Task；错误状态不伪装为零数据；关闭发起终端后服务可用 |
| 当前 | 完全重复样本在派生版本中受控去重 | 人工审批后执行；Parent 摘要不变；Child 独立检测；冲突与缺证继续保留责任项 |
| 当前 | 同机执行归属与显式中断恢复 | OS锁自动释放；活跃执行不能接管；新任务重新审批；保留历史文件 |
| 当前 | 能力目录与任务用量 | 配置不等于连接；供应商报告、估算、重试和未知费用分别显示 |
| 当前 | 离线备份与新目录恢复 | 确认停写后逐文件核验；不覆盖原目录；不宣传为在线备份 |
| 后续 | 多机调度与细粒度 checkpoint | 跨主机的执行租约、工具幂等性与故障恢复需单独验证 |
| 后续 | 团队使用和部署 | 经部署环境验证的身份认证、角色授权、数据库备份及恢复 |
| 后续 | 领域扩展 | 用同一工具合同接入其他视觉数据格式和行业规则，并验证迁移效果 |

这些是演进方向，不能全部写成已完成能力。当前更有用的目标是把“发现数据问题 → 责任人处理 → 新版本验收”这一段流程做完整，再增加通用平台能力。

## 开发与验证的分工

生产任务使用真实服务、存储和工具。测试在隔离目录构造输入、模拟故障并核验结果；它们不参与用户任务的决策。合成演示、公开只读回放和用户本地数据必须保持清楚的来源标识。
