# VisionData Gate 技术路线（简明版）

## 一句话理解

它不是替工厂判断产品好坏的缺陷检测器，而是替视觉数据团队把“收到一批图和标注”推进到“问题有依据、整改有版本、结果有复验”的数据交付工作台。

完整算法、状态和代码映射见[当前技术路线](PROJECT_TECHNICAL_OVERVIEW.md)。

## 用户完成的六步任务

1. **确认用途**：这一批数据要训练、验证、测试还是交付；谁处理问题、谁复核。
2. **冻结输入**：记录图像、标注、划分、规则与版本身份，原输入保持只读。
3. **工具测量**：检查图像质量、重复／泄漏、标注结构、工况覆盖和元数据漂移。
4. **Agent 补证**：只有出现冲突、新证据、工具故障或缺口时，才选择专项 Worker；同时记录为什么选和为什么不选。
5. **人工批准整改**：Agent 可以建议，具名人员批准具体版本上的具体动作。
6. **Child 独立复验**：在派生版本按同一合同再检查，分别报告持续项、新增项和真正满足关闭条件的责任项。

## 为什么 Agent 有必要

固定流程足以处理已知且稳定的检查。项目的架构对照也显示，固定 SOP 下增加 Agent 数量不会自然提高质量。

Agent 的作用是处理**中间事实会改变下一步**的任务：比如重复检查与 metadata 冲突、主要工具超时、新证据推翻原假设、剩余预算不足。此时系统要重新选择检查、保留失败、决定停止点并请求人工，而不是全量调用所有工具或让大模型猜答案。

## Agent、工具和人如何分工

| 角色 | 可以做 | 不可以做 |
| --- | --- | --- |
| 确定性工具 | 测量、比较、返回 Finding 与阈值 | 判断业务根因或批准生产 |
| Agent 内核 | 管理状态、假设、缺口、预算、Worker 和失败恢复 | 把模型文本改写成测量事实 |
| 外部 Planner | 在 off／shadow／gated／replay 模式下提供受控建议 | 绕过规则和具名人工闸门 |
| 具名人员 | 批准 CAPA、接受或拒绝候选、承担最终判断 | 由系统匿名代签 |

## 模型学习处于下一段

通过治理的数据可以进入受控训练：绑定数据版本、父模型、预算和环境，产生候选权重，再做独立评测和人工选模。模型错误先被分类为标签问题、困难样本、新工况或信息不足，然后才形成下一轮数据任务。

当前有 CPU 参考学习、受权 YOLO detect 路径和 Normality 分支。持续学习模块负责检查给定的遗忘矩阵；TTT／RL 仍是研究位置，不属于已完成训练能力。

## 证据边界

- DynamicBench-v3 验证合成冲突与故障下的重规划，不是工厂准确率。
- Omni 历史授权离线试跑证明真实文件处理与负结果保留，不是可公开原始数据或客户验收。
- Pages 处理浏览器本地图像并展示独立合成案件；完整可写闭环在本地 Web／桌面运行。
- JCS／SHA 提供可复算完整性，不等于数字签名或不可重写存储。
